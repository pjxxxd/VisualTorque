# VisualTorque — Qwen3.5-27B BF16 LoRA Weight-Shortcut Study (96GB)

This notebook performs one controlled task-specific fine-tuning experiment on the official non-quantized **Qwen3.5-27B** checkpoint. Its scientific question is not merely whether supervised fine-tuning improves accuracy, but whether it changes the model's reliance on the total-weight shortcut.

The default run is deliberately **outcome-only and rationale-free**. It does not supervise weight, distance, torque, chain-of-thought, or hidden states. Therefore, any post-training change in causal routing cannot be attributed to explicit intermediate-variable labels.

## Frozen data design

| Role | Source | Use |
|---|---|---|
| SFT train | Dataset v1 \`probe_train\` only | Balanced across the 3 × 3 table of total-weight cue × physical outcome |
| Checkpoint selection | Dataset v1 \`probe_dev\` only | Validation loss; never used for gradient updates |
| Final behavioral test | Dataset v1 \`probe_test\` only | Held-out unit-distance combinations and held-out multi-stack structures |
| Primary shortcut diagnostic | A no-replacement balanced subset of \`probe_test\` | Equal support in every weight-cue × outcome cell |
| Later mechanism tests | Existing frozen Qwen-27B protocols | Run only after the adapter and manifest have been saved |

For every selected training scene, the notebook uses exactly three option permutations: one whose correct label is A, one B, and one C. Thus answer-token frequency is exactly balanced. The training scene occurrences are also exactly balanced across:

\[
\text{weight-only prediction}\in\{L,B,R\}
\quad\times\quad
\text{physical outcome}\in\{L,B,R\}.
\]

A classifier that uses only total weight therefore obtains exactly chance-level accuracy on the realized training manifest. The untouched test distribution is reported both naturally and through the balanced diagnostic subset.

Run in a fresh Google Colab session with one RTX PRO 6000-class GPU exposing at least 88 GiB. Outputs and resumable shards are written under \`VisualTorque/results/qwen27b_bf16_lora_weight_shortcut_v1\` on Drive.

## 1. Protocol, dataset construction, and leakage barriers

The split is fixed before loading the model. The notebook refuses to proceed if any weight-cue × outcome cell lacks enough unique training support, if the three source splits overlap, if held-out factor combinations leak outside `probe_test`, or if the realized training manifest permits a total-weight classifier to exceed chance.

## 原单元格 12

## 2. Pre-training behavioral measurement

Before inserting any adapter, the official BF16 checkpoint is evaluated on all six answer mappings for every frozen `probe_test` scene. Scores are aggregated in semantic left/balanced/right space, so stable A/B/C token preferences cannot masquerade as a physical strategy.

<a id="cell-15"></a>

## 原单元格 15

## 3. Decoder-only BF16 LoRA

LoRA is attached to linear modules discovered inside all 64 decoder layers. Adapters accidentally injected into similarly named vision modules are explicitly frozen. The visual encoder and multimodal projector therefore remain unchanged in the primary experiment.

The loss is applied only to the exact one-letter answer and end token. Prompt, image tokens, and option text are masked. This is intentionally not chain-of-thought or intermediate-variable supervision.

<a id="cell-19"></a>

## 原单元格 19

## 4. Frozen post-LoRA test and causal handoff

The identical six-mapping `probe_test` set is evaluated after training. The primary behavioral estimands are balanced-test accuracy, conflict accuracy, and the rate at which predictions follow the wrong total-weight cue on conflict scenes.

These measurements answer whether the shortcut changed behaviorally. They do **not** by themselves prove that a distance/torque circuit was learned. The final cell records the adapter identity needed to rerun the existing frozen mechanistic protocols and to conduct a separately split post-LoRA layer-relocation scan.
